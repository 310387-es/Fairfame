# 23 — Build log

The decision record for everything built so far, phase by phase and wave by
wave. It lived at the top of `CLAUDE.md` until 9 Aug 2026, when that file passed
the 150k-character limit the agent tooling enforces — 135k of its 160k was this
one section.

**It was moved rather than trimmed, deliberately.** Almost every entry here is a
decision *and the argument for it*: why the badge's average ignores the approval
gate, why `iys_uploaded_via` exists, why a DM cannot be published, why the SLA
clock stops when the shop does. Those arguments are what stop a rule being
quietly re-litigated by somebody who only sees the code that came out of it. A
summary would keep the conclusions and lose the reasons, which is the half worth
less.

`CLAUDE.md` keeps the operative rules — the ones that constrain the next change —
and points here for why any of them is the way it is. **Read this before
reversing a decision**; there is a fair chance the alternative was tried and the
entry says what went wrong.

On the Analytics tables, the heatmap, the benchmark and the requests table.

Duplicating the universal lines six times would be six copies to keep in step for nothing.

    - **A form failure speaks Turkish.** B3 made four silent forms speak and they spoke **English** — a blank campaign name returned Zod's own default, "Too small: expected string to have >=1 characters", to a café owner in Kadıköy. The fix is that a schema yields a **key** and `useAction` renders it, because the client is the first point in the round trip that knows who is reading; `src/lib/validation-keys.ts` is a **leaf module with no imports at all**, since the natural home beside `toFieldErrors` reaches `@/auth/session` and therefore `pg`, and a `"use client"` file importing a *runtime* value from there fails the build — the rule that put `search/types.ts` where it is. **Zod 4's own `tr` locale is deliberately not used**: `z.config` is process-wide, so two concurrent requests in two languages race for one setting, and its prose is a compiler's rather than a product's. The **summary** is translated only where there are named fields — the other eighty-odd `invalidInput` sites pass "Unknown widget."-style strings reached by a malformed request rather than by a person filling in a form, and translating forty defensive sentences nobody can reach costs a key each and tells nobody anything. Verified in Chrome in both languages: "Bu alan zorunlu." / "This is required.", with "İşaretli alanları kontrol edin." above it.

It fails safe in that direction and **not in the other**: a key existing only in a comment counted as *used*, which is how `feedback.updated` sat in both catalogues referenced by nothing. Comments are blanked before scanning, string literals matched first so a `//` inside a URL survives, and the dead key is gone.

Nothing leaked, because `resolveActiveLocation` re-checks the id against what the new tenant can see; what was wrong is that the fallback was incidental rather than intended. **Remembering a branch per organization is deliberately not built** — it means a cookie per client or a map inside one, which is a parser and an eviction rule for a convenience.
    - **The `analysis-jobs` flake was a real race in the test harness.** `drain()` returned the instant `wait + active + delayed` hit zero, and these jobs enqueue each other: between a processor returning and its child appearing in `wait`, every count reads zero and the queue is not finished. So `first` was captured before the notify job ran, the alert landed, and the second half counted one more than it started with. It waits for three *consecutive* quiet polls now — the difference between checking a condition and checking that it has settled. Three consecutive clean runs of that file, then the full suite.

## The name — Fairfame (10 Aug 2026)

**The product has a name, and it is not the one every doc in this folder was written under.** Identity, rules and reasons: [`24-brand-guidelines.md`](./24-brand-guidelines.md); the commercial argument and the open gates: [`05-business-model-and-gtm.md`](./05-business-model-and-gtm.md) §6. This entry records why the decision went the way it did, because that is the part a later reader cannot reconstruct from the assets.

- **The shortlist was competing in the wrong territory.** Every candidate on it named *what the software reads*: a review, an opinion, a voice. That is product territory, it is crowded, it registers badly, and the availability problem the shortlist kept running into was a symptom rather than bad luck. **Fairfame names the outcome instead** — what the business is left with. It is the pattern the category's own winners already took: Podium and Birdeye name a result and a vantage point, and nobody had to be told what "review management platform" meant to remember either.
- **"Fair fame" is a found phrase, not a coinage** — real English, early-modern through the 19th century, meaning *good reputation, honourably earned*. The second half is the compliance posture stated in two words: no review-gating, consent before every send, an İYS gap named rather than hidden. In a market whose grey edge sells manufactured reputation, a name that says *earned* is doing argument work, not decoration.
- **It survives Turkish**, which several of the alternatives did not: no `w`, `q`, `x`, no hard `c`, and *fair* already arrives through *fair play*. Suffixes take an apostrophe — Fairfame'e, Fairfame'in — so TR copy declines it rather than avoiding it.
- **Adopted at risk, deliberately.** TÜRKPATENT and EUIPO (classes 9, 35, 42) are unscreened and `fairfame.com` is unbought — a HugeDomains fixed-price listing, so a purchase rather than a negotiation. Neither gate is closed and nothing customer-facing ships until both are. The risk is accepted because the reversible cost is small and known: **the name is display copy only.** No table, module, route, env var or test identifier carries it, which is the rule the sweep below is bound by, and it is what keeps a failed screening a copy change rather than a migration.
- **The identity had to be argued twice.** v1 was judged too plain; v2 added the editorial voice — Lora for display, the circular seal replacing a rounded-square tile that read as any app icon, the amber full stop. v2.1 then **removed the amber dither texture** and replaced it with the murmur, because the dither sat close enough to a reference brand's signature to be theirs rather than ours. The murmur says the same thing in the brand's own material: the town talking, in words, in both languages.
- **The sweep is display copy only, and the line is drawn at contracts.** Catalogues, email subjects, the Stripe line item, the PDF's author and footer, page-title fallbacks, the agency default, the sender name, the download prefixes. Not renamed at this point, deliberately: cookie names, the app's database role, the embed attribute (it is on other people's websites), the postMessage type, the logger's `app` field, the İYS gateway symbol, test hostnames. *(Superseded — the two later entries below took all of them.)* Those are identifiers a rename can only break. Three comments keep the old name because they explain what was replaced, and `docs/README.md` lists all of it so the next person does not "finish the job".
- **Renaming found a bug the rename did not cause.** The Connections screen drew *our own* source, `firstparty`, as an "R" monogram in `#4F46E5` — a fifth indigo, in the one file exempted from the token rule because "a brand colour is a fact about another company". It wears the seal asset now and the stray hex is gone, which makes that file's exemption true as written for the first time.
- **The brand is a layer, and it stops at the product's edge.** Paper, Lora and the murmur are for marketing, documents, email chrome and print; the app keeps [`15`](./15-design-system.md) and [`21`](./21-visual-language.md) exactly as they were — cool canvas, Geist only, no texture. The shared ink, amber, indigo and seal are what make it one company. Stated in `CLAUDE.md` because it constrains the next UI change: the temptation after a brand lands is to bring the serif indoors.

## Two report-PDF defects, found while proving the rename (10 Aug 2026)

The brand sweep claimed to have changed "the PDF report footer", and checking that claim rather than the source is what turned these up. Neither is a branding bug; both were there before.

- **The footer had never rendered — fixed.** `styles.footer` said `position: absolute; bottom: 28`, which is the obvious way to put something at the foot of every page, and it put nothing anywhere. Every scheduled report this product has produced went out with no brand line, no generation date and no "1 of 2". Nothing threw; the tables above it were correct; the only evidence was a band of white paper at the bottom of a document nobody proof-reads that far down.
  - **The cause is one property.** Reproduced against `@react-pdf/renderer` 4 in a five-line document: a `fixed` child positioned with `bottom` is laid out off the paper when the **`Page` carries a `lineHeight`**. The child's own `lineHeight` makes no difference, and no value of `bottom` — 0, 28, 56, 100, a percentage — brings it back. `top` is unaffected.
  - **The obvious fix is the wrong one, and it was rendered before it was rejected.** Moving the leading off the `Page` onto the text roles it was feeding *looks* equivalent and is not: measured band by band it shifts the summary card a few points **and clips the first glyph of a right-aligned cell** — "Sentiment" printed as "entiment", "4.3" as ".3" — in a document that goes to a customer. Wrapping the content in one leading `View` pushes the last table 135pt down; dropping the leading altogether pulls it 35pt up. Anchoring the footer from the top changes nothing else on the page at all, so that is what shipped, with A4's height written down as the fact it is.
  - **`tests/lib/report-footer.test.ts` exists to stop the tidy-up.** `top: 802` next to a `bottom: 28` that reads more naturally is exactly what a later reader corrects, and the regression is invisible in review, in the unit suite and in the browser suite — it is only visible in a rendered PDF. The test asserts the element tree, and it was confirmed to fail when the property is put back.
- **A second, still open: two reports rendered in one process lose glyphs.** `pnpm email:preview` with both locales produces an English report reading "entiment" and ".3"; the same run with `--locale en` alone is perfect. **Reproduced on unmodified code**, so it predates all of this and is not the footer fix. The shape of it points at the subset font being built once and reused for a document that needs glyphs the first one did not — and it matters well beyond the preview script, because **the worker renders a report per schedule in one long-lived process**. Not fixed here: it is a font-subsetting investigation, it has nothing to do with a rename, and it deserves its own change and its own test. Recorded rather than carried quietly.

## The front door, rebuilt from the approved concept (11 Aug 2026)

`/` now renders `brand/fairfame-landing-concept.html` (v4) as a real Next.js page: murmur hero → five-step flow tour → nine-cell bento with vignettes → system map → agency band → public pricing → pull quote → five questions → ink CTA. Structure and copy are the concept's, verbatim, in both languages. **What was there before was the *earlier* front door** — the "briefing is the page" build, with the murmur and Lora added afterwards — and the two were easy to confuse: the concept's copy dictionary has 158 keys per language and the shipped `marketing` namespace had 119 entirely different ones, with no FAQ, no quote band and no map. Auditing the key sets rather than the screenshots is what made that obvious.

- **The prototype's palette turned out to be the product's palette.** Every hex the concept hardcoded inside its mock product window — `#F6F7FB`, `#E7EAF3`, `#666E88`, `#3D5AF1`, `#F3F5FA`, `#EFF1F7` — resolves exactly to `--canvas`, `--line`, `--ink-350`, `--indigo-600`, `--line-soft`, `--line-inner`. The designer had eyedropped the app. So the window is drawn in **product tokens and the product's type ramp**, and only the page *around* it is the brand layer. `globals.css` already made this argument for the briefing card ("a demo that renders the product in a typeface the product does not have is a demo that lies about what you get"); it holds for colour and size too. The whole concept mapped onto the existing ramp — poster, hero, display, lead, title, body, copy, meta, eyebrow — without inventing a step.
- **The brand tokens are declared on `.marketing`, never on `:root`.** Four genuinely new warm values (`--paper`, `--paper-line`, `--paper-faint`, `--paper-body`) plus two that *point at* product tokens rather than restating their hex, because `docs/24` §3 says the brand's ink **is** `--ink-800` and its rail **is** `--ink-900`. Amber and indigo need no entry at all — the page uses the product's directly. `tests/lib/brand-contrast.test.ts` asserts both halves: the ratios, and that no cool value is ever copied into the block. The Tailwind `--color-*` utilities are global because that is the only place Tailwind reads them; the *values* are scoped, so `bg-paper` outside `.marketing` resolves to nothing and paints nothing. **The scope is the variable, not the class**, which is what makes "the brand stops at the product's edge" a fact about the cascade instead of a convention.
- **`--ink-400` is illegal on paper, at 4.37:1.** Legal on white, where it was chosen. That is the entire reason `--paper-faint` exists rather than the page borrowing the app's muted ink, and the failing value is asserted so nobody reaches for it.
- **The concept's node-measuring loop is an infinite loop in React, and only a human found it.** The map sized each label's pill by `getBBox()` and writing the result to state — measure, re-render, measure. Ported directly it threw "Maximum update depth exceeded" on first paint. It passed `pnpm verify` (2,308 tests), the production build, and the browser contrast and touch-target suites **before failing on the first look at the page**, which is the re-test gate's argument in one incident. The fix removes measurement rather than repairing it: each label is a `<foreignObject>` holding an inline-block span, so HTML sizes it — correct in both languages, correct before and after the webfont, with no cycle to get wrong.
- **Two guardrails caught things this change would otherwise have shipped.** `design-contrast.test.ts`'s completeness half demanded a ruling on five newly-painted backgrounds; `naming-collisions.test.ts` caught "QR campaigns" in the new copy and made it justify itself (it is the `/get-reviews` entity, named correctly, so it is allowed by name). Both are the enumeration-test pattern working exactly as `docs/22` intended.
- **Three deliberate departures from the concept, each because the concept is a desktop prototype.** (1) It hides the nav links *and* the call to action below 900px, leaving a phone with a logo and a language button — replaced with a real disclosure that closes on Escape, since `docs/18` measures this page at 390px. (2) Its benchmark vignette drew "Fairfame 86%" against an anonymous "~ 64%", which is a comparative claim about us and one `PRODUCT.md` forbids — and is not what the feature does, since the product scores a *business's* branches. Two branch names make the same picture true. (3) Its rating figure "4,8" was a literal; it is a message now, because a comma decimal is wrong in English on a page whose pitch is that Turkish is not a translation.
- **The language control is a two-sided toggle, not the shell's dropdown.** There is no locale routing in this app — `src/i18n/locale.ts` is a cookie — so a per-locale link would be an anchor with no destination. It writes the same cookie through the same server action, so there is one mechanism rather than two.
- **The FAQ is `<details>`.** A downgrade in machinery on purpose: the element already gives a keyboard the toggle, a screen reader the state, and find-in-page the ability to open the panel it landed in, and it needs no client bundle.
- **The reveal renders plain and hides itself on mount**, never the other way round. `.reveal` is `opacity: 0`, so shipping it in the server markup would mean a blank page for anyone whose JavaScript failed. A marketing page that is invisible without a bundle is worse than one that does not animate.
- **`briefing.tsx` and `pipeline-flow.tsx` are deleted**, so `/` no longer composes a real digest through `getSampleDigest()`. That property is not lost — `/sample` still serves it, and the footer links there, which keeps one checkable artefact behind the page. Recorded because it *was* an argued property of the previous build.
- **Pricing is USD on `/`, in both languages**, at $29 / $89 / $229 with Agency per deal. See `05` §2: two of the three sit above the bands that section first hypothesised, and the TRY ladder is unchanged but no longer appears on the front door.

### Revised the same day, after the first review

- **The language control is the app's `LocaleSwitcher` after all, and the reason is a future one.** The EN/TR toggle was the better control for exactly two locales and the wrong one for a product that expects more: a toggle is a claim that there are two, made in markup, so a third language would have meant rebuilding the component rather than adding a row to `LOCALES`. The shell's switcher already reads that array. **This is the general shape of the mistake worth remembering** — a control shaped to today's data is a control that has to be rewritten when the data grows, and the cost of the general one here was a `className`.
- **The hero fills the first screen and centres in it, with the murmur behind the whole width.** It was a left-aligned column with the carve offset to `carveX: 0.3`. `carve` clears an ellipse and the words gather *around* it, so the carve has to sit where the content sits — centred content and a centred carve put the phrases in both margins, which is what makes the texture read as a background rather than as decoration pushed to one side. Height is **`min-h-[calc(100svh-4rem)]`**: `svh` rather than `vh` because `vh` is the viewport with the phone's browser chrome retracted, so a `100vh` hero hides its own call to action under the address bar until you scroll; `min-h` rather than `h` so a long Turkish headline makes the section taller instead of overflowing it.
- **`murmur.js` gained `opts.opacity`, and it is the third backwards-compatible hook that file carries.** A multiplier on the *resting* alpha (10% ink, 34% amber), clamped at 0.6, default 1 — the front door passes 1.5. It lifts only where the words settle, so the sharpening toward the pointer still has somewhere to go, and the clamp is what stops a multiplier turning texture into content sitting behind a headline. `docs/24` §5 records it beside `opts.family` and the `detach` return, for the same reason those are recorded: a regenerated copy that drops it takes the front door's look with it.
- **The system map moved onto ink, because nine white cards precede it.** A tenth white card reads as a tenth feature rather than as the thing tying the other nine together; on ink it is a band, like the closing call to action, which is the page's other "this is the whole of it" moment. It also fixed the amber flow, which on white was a pale dotted line and on ink reads as current through wires. The seal switches to the on-dark file rather than being tinted — tinting is a redraw.
- **The map's hover was rebuilt around what makes a highlight legible.** Two faults, both real. The handlers sat on the 280-unit `foreignObject` row rather than on the pill, so an edge lit up whenever the pointer crossed the empty space beside a short label — most of the column — which made it feel like it was firing at random. And lighting one edge among ten identical ones barely registers: **the readable version dims the other nine to 25%** rather than brightening the one. Nothing moves; only opacity and stroke.
- **The footer's "name adopted pending trademark screening" line is gone.** The gate itself is unchanged and still open — it is recorded in `PRODUCT.md` and `24` §8, which is where an internal caveat belongs. A sales page is not the place to publish one.

### And again, after the second review

- **The murmur lost its carve and gained a scrim, which is the better version of the same rule.** `carve` clears an *ellipse*, and with a centred hero that ellipse sits exactly where the eye goes — so the composition read as a ring of words around a hole rather than as a background. It now seeds across the whole hero, and what keeps the copy legible is a radial paper wash painted behind the text block. The distinction is worth keeping: **carve removes the texture and leaves a shape; the scrim veils it and leaves a field.** The rule the carve protected — no body copy over a moving texture — is unchanged, it is enforced by a gradient now. The wash lives in `page.tsx` rather than in `MurmurField`, because a caller with a different layout wants it somewhere else or not at all. **The phone still gets no murmur**: a 390px hero has no margin for the words to gather in, and that reason is untouched by any of this.
- **Ten phrases were never going to be enough, and the fix is arithmetic rather than taste.** The canvas seeds about one word per 26,000 square pixels — ~46 on a 1440-wide hero — so a ten-phrase list showed the same sentence four or five times while others never appeared. Two changes: the catalogue carries **28 per language** (each its own copy, invented and anonymous per `24` §5), and `murmur.js` now **deals from a shuffled deck** instead of picking at random. Independent random picks cluster; dealing guarantees every phrase is used once before any is used twice. A rejected position **returns its card**, or a phrase could be dealt, fail to fit and never appear — which is the uneven distribution the deck exists to remove, arrived at more slowly.
- **The language menu lost its "Language" caption row.** The trigger already carries a globe and the accessible name, and every item is the language written in its own language, so the caption restated the icon and cost a row in a menu that only ever holds locales. The name stays on the trigger's `aria-label`, where a screen reader reads it *before* the menu opens rather than after. Changed in the shared shell component, so the app gets it too.
- **The map's pills align inwards, and that is what closed the gap.** They were pinned to the page margin with every wire starting at one fixed x — so because the labels are different lengths, each wire had a different-sized run of empty space in front of it, a long label nearly touching its wire and a short one floating a hundred units away. Sources now hug the *right* of their column and outputs the *left* of theirs, so **every pill meets its wire at the same small gutter** and the ragged edge falls on the outside, where nothing is attached to it. It costs no measurement, survives a language with longer words, and it is the shape the diagram is about: a funnel. *(Superseded the same day — see below.)*

### Fourth pass: the veil, and why a scrim was never going to work

- **A wash over the canvas fades pixels; the murmur needed something that fades words.** The scrim kept the copy legible and cut every phrase that crossed its edge in half — a sentence stopping in the middle of itself, which reads as a rendering fault rather than as depth. `murmur.js` gained **`opts.veil`**: each word's alpha is scaled by how deep its *own centre* sits in an ellipse, measured once at seed time and stored, so the whole phrase fades together and the drift cannot make it flicker. The scrim is gone; the field is continuous through the middle and every sentence in it is whole.
- **Two details, each found by looking at the render rather than by reasoning about it.** The veil has to scale the **pointer-proximity ceiling** as well as the resting alpha — otherwise moving the cursor over the headline sharpens the words underneath it back to full strength, which is exactly where they must not be. And the ellipse's inner 72% is held **flat** rather than ramping from the centre: a text block is a rectangle inside an ellipse, so its corners sit far enough out that a centre-start ramp has already given most of the opacity back, and the words at the edges of the copy were as loud as anywhere on the page.

### Third pass: crowd, speed, and the map's final shape

- **`murmur.js` gained `density` and `speed`, and the density one carries a dependency worth stating.** `density` multiplies the seeded count, which is derived from area (~one word per 26,000 square pixels); the front door runs `2`, so a 1440-wide hero holds ~90 phrases instead of ~46. The collision spacing **relaxes as the square root of density** — words tile a plane, so twice as many need their gaps cut by about √2 to fit the same area, and without that the denser target simply cannot be met and the extra words are dropped in silence. `speed` scales the drift's two sines and *not* their amplitude, so the crowd stirs faster without travelling further.
- **Crowding the field is a copywriting cost, not a config change.** The deck deals every phrase once before any repeats, so ninety words on screen need forty-eight phrases to stay inside "nothing appears more than twice". The catalogue went 10 → 28 → **48 per language**. This is the rule to remember when somebody next asks for a denser murmur: **the density knob and the phrase count move together**, and a murmur that repeats itself reads as a bug rather than as a crowd.
- **The scrim's opaque stop has to clear the *last* line, not the headline.** The first version held paper to 42% and faded by 78%, which looked right because the headline is enormous and sat dead centre — and left the source list, the smallest and faintest type on the page, over drifting words at the bottom of the ellipse. **The automated contrast suite cannot catch this**: `e2e/contrast.spec.ts` resolves an element's background by walking its ancestors, and the murmur is a *sibling* canvas, so the test reads `--paper` and passes whatever is painted behind. Found by looking. Stops are 58%/88% now, with padding generous enough that the fade happens outside the text.
- **Fifth and final shape: one path per node, and the pill sits on top of it.** The HTML lead below could not carry the travelling dash — a `stroke-dashoffset` animation runs over an SVG path's own length, so a separately-drawn straight lead would have had its own phase and the dots would have stuttered at the join. The wire is now **one path** from the card's edge to the seal (straight run, then curve), and it passes *behind* the node; the pill is opaque, so the visible line begins exactly at the pill's edge whatever the label's width. **The problem that had needed four attempts turns out to be solved by paint order rather than by arithmetic**, and still with nothing measuring anything.
  - One consequence, found by looking: the wire running behind the node means **the pill must not dim with it**, or the dashes show straight through the label. Only the wires drop to 25% now — one white pill among nine muted ones is already an unmistakable highlight, and every node stays readable while the reader follows somebody else's connection.
- **Fourth shape (superseded above): the node hugs its label and a *lead line* reaches the wire.** Filling the column had made "Google" a wide box with an empty right half — smaller type and a narrower column shrank the box without fixing the shape. The pill is now sized to its own words and sits against the outer margin; the rest of the row is a **flex-1 hairline** running from the pill's edge to where the bezier starts. That resolves the three constraints that had been knocking each other over for four revisions — the node hugs its label, the diagram still spans the card, and every wire still touches its node — and it does it **without measuring anything**, because a flex child taking the remaining width is the browser doing the measurement. The measure-render loop that broke this component originally stays gone. The lead is solid while the curve beyond it carries the travelling amber: a node reads as having a stem that joins the flow, and it is far less machinery than re-implementing an animated dash in CSS to meet an SVG one in phase.
- **Then the balance: smaller nodes, longer wires.** `COLUMN` went 280 → 200 and the label dropped a step down the ramp (`text-copy` → `text-meta`, with tighter padding and a 30-unit row), while `SEAL` went 44 → 38. Both are levers on the same thing — **the wires run from the column edge to the seal's edge, so every unit off either end is a unit added to all ten runs** — and together they take each run from 120 units to a little over 200 against a 200-unit node. The picture stops reading as two stacks of buttons with something drawn between them and starts reading as a network with labels on it. 200 clears the longest label either language produces (both land near 170 units including padding), verified by measuring `scrollWidth` against `clientWidth` on every node in both locales rather than by looking at it.
- **The map's pills fill their columns, which is the third shape and the one that works.** Sized-to-content pills at the page margin gave every wire a different-sized gap; pinning them inwards fixed the wires and emptied the outer margins, so the picture sat in the middle of a wide card with dead space at both ends. Filling the column fixes both — every pill starts at the card's edge and ends at the wire, so the gutter is uniform *and* the diagram spans the card. It costs the ragged silhouette, which was carrying no meaning, and it buys a node that **cannot be clipped by a longer word in a language nobody has added yet**, because the box no longer depends on the text inside it (it ellipsises instead). The hover note moved with it: the pill now *is* the row, so a handler on the row is honest.

## Two defects in the front door's anchors (11 Aug 2026)

Both reported from the running page, and neither is visible in the source without knowing what to look for.

- **Every anchored section landed behind the masthead.** `scroll-margin-top` was 0, so clicking "Questions" scrolled the section's top edge to the *viewport's* — 65px underneath a bar that is `sticky top-0`. The section's own 56px of padding went behind the masthead and the heading arrived 5px below it, which reads as a scroll that stopped just short of where it was aimed. One rule in `globals.css` on `.marketing section[id]`, not a utility class per section, because the failure mode of the utility is a section added later that forgets it.
- **A same-page `<a href="#faq">` breaks the back button, and the mechanism is worth keeping.** A plain anchor is a *browser* navigation: it pushes a history entry the App Router never saw, so `history.state` on that entry is `null` rather than Next's route tree. Coming back into it the router has no tree to restore, leaves whatever is currently mounted, and lets the browser change the URL underneath it — the visitor reads the FAQ, signs in, presses back, and watches the address bar say `/#faq` while the sign-in form stays on screen. **It takes three steps to surface**, which is why the page had been driven by hand without anyone hitting it: jump to a section, leave the page, come back. Nobody clicking the front door in order does that; everybody who reads a question and then signs in does.
- **The obvious fix is half a fix, and it was caught by re-testing rather than by reasoning.** Swapping in `<Link href="#faq">` restores the history entry and *drops the scroll*: Next treats a push to the URL the reader is already on as nothing to do, so a visitor whose address bar still says `#faq` can scroll away, click "Questions", and watch the nav do nothing. Both halves now live in `src/components/marketing/hash-link.tsx` — `Link` for the entry, an explicit `scrollIntoView` for the movement, which is the one thing that must happen on every click whatever the URL already says. `scrollIntoView` honours `scroll-margin-top`, so the two fixes compose rather than fight. **Every same-page anchor on the marketing surface goes through it** — the nav's five, the hero's, pricing's, agency's, and the skip link.

## One ladder in USD, and quotas that scale with what is being billed (11 Aug 2026)

Rationale and the competitor scan are in `docs/05` §1–2; this records what the code now does and why the shape changed.

- **The TRY catalog was a fact about the go-to-market wearing a product decision's clothes.** It existed because Türkiye is where the first customers are — which `CLAUDE.md` already says is not a fact about the product — and it bought a second price list to reprice against inflation on a schedule nobody owned. The catalog is USD cents; the provider converts at charge time. **`plans.currency` stays on every row**, and the formatter still reads it: one value in a column is not the same as no column, and hardcoding `₺` or `$` is how a price ends up rendered in a currency nobody is charged in.
- **A cap was replacing a sale.** "Max 3 locations" meant a fourth branch was a tier jump — the customer's growth read to them as a penalty and to us as churn risk. `included_locations` is what the base price buys and `price_extra_location_month` is what the rest costs, so **`max_locations` survives as the tier's ceiling rather than as the thing being sold**. The two are deliberately separate columns and a test pins that no plan includes more than it allows.
- **The quota rule is the substantive change, and it is one line of arithmetic with a wide blast radius.** `requests_per_month`, `ai_analyses_per_month` and all three metered keys are **per location** and multiplied by the organization's location count. Billing is per location, so allowances have to scale with it or a five-branch Growth account pays five times and gets throttled on the fourth day. The catalog therefore stores the *single-branch* figure, which is also what makes the tiers comparable to each other and to a competitor's pricing page.
- **Three keys deliberately do not scale, and the reason is a loop.** `max_locations`, `max_team_members` and `max_widgets` stay absolute. A location cap multiplied by the location count is **a cap that raises itself every time somebody reaches it** — one branch becomes unlimited branches, and the limit never binds. `scalePerLocation` lists the five keys it touches rather than excluding three, so a new key is opted in by a human rather than by default.
- **Overrides apply before multiplication, and the order is load-bearing.** An override *replaces* a plan value, and plan values are per-location figures, so an override is one too. Scaling first would multiply the plan's number and then throw it away, making every custom deal silently absolute while every ordinary account scaled. Checked before assuming: the only other reader of `subscriptions.overrides` is `src/agency/branding.ts`, and it reads the `white_label` boolean — no numeric consumer assumes absolute.
- **Null stays null, zero stays zero, and the count floors at 1.** Unlimited never multiplies into a number; a plan granting no SMS grants none at ten branches (the arithmetic half of this codebase's "absence is `null`, never `0`"); and an organization that has not created a location yet gets one branch's quota rather than nothing, because zero would fail the very first review request a new account makes.
- **Seven database tests failed, and five of them were the same mistake.** They spent an allowance by writing a literal `250` into `usage_counters` — the old catalog figure. Under the new rule that literal is no longer the ceiling, just a number below it, so the code correctly kept working and the tests correctly went red. They now **derive the ceiling from `withinLimit` itself**. Two of them, in `tests/db/replies.test.ts`, were asserting "still works when the allowance is spent" against an allowance that would not have been spent — a green test measuring nothing.
- **The one thing left open, and it is a packaging decision rather than a bug.** `docs/05` §2.1 calls Agency's metered allowances "pooled" — 2,500 for the whole agency — but `scalePerLocation` has no plan exception, so a 40-location agency resolves to 100,000 SMS credits. A `planKey === "agency"` branch is exactly the hardcoding `CLAUDE.md` forbids, and `subscriptions.overrides` cannot express it either because an override is multiplied too. Either those numbers become genuine per-location figures (2,500 ÷ 10 = 250, which lands level with Pro) or the catalog needs a `meteredPooled` flag. Written down in `src/lib/plans.ts` beside the values rather than fixed by guess.
- **The front door was quoting eight hardcoded numbers, and one of them was a sentence about a billing model we no longer have.** `/` rendered its prices from four message-catalogue strings per locale — correct only because somebody had lately typed them correctly — and labelled them **"/ location · month"**. Under base + extra that is false in both directions: it reads as though Starter's $29 multiplies by branch, and as though Pro's $229 buys one. Prices now come from `PLAN_CATALOG` and the unit says what is true. **The catalogue, not the `plans` table**: identical values, but `/` is public, unauthenticated and heavily cached, so a query buys nothing and an unseeded database would render a pricing section with no prices in it.
- **"from" appears only where an extra location can be bought.** Starter has none, so $29 is not a starting price, it is the price — and overstating cost in the one card a first-time visitor reads is the wrong direction to be wrong in. Derived from `priceExtraLocationMonth === null` rather than from the plan's name.
- **The FAQ was the same bug, hidden better.** `faq.a4` spelled all three figures out again *and* repeated "per location, per month". An answer folded inside a `<details>` is the copy nobody re-reads after a repricing, so it now interpolates from the same catalogue.
- **`t.rich`, because the words are not in the same order in both languages.** English is `from $89 / month`, Turkish is `aylık $89'dan` — "from" is a prefix in one and a suffix in the other. A big-number-beside-small-unit split looks right in English and puts the pieces in the wrong places in the launch locale, which is the trap `src/components/billing/plan-section.tsx` already records. The translation marks the figure with a tag and decides the order itself.
- **That broke `tests/lib/i18n-messages.test.ts`, correctly, and the fix widened it.** It renders every message through next-intl to prove it compiles, using plain `t()` — which reports a missing handler for any tag and returns the key. So the check could not validate a rich-text message *at all*, and the first one added was always going to fail there. It now renders tag-bearing messages through `.rich` with stub handlers, so the coverage grew rather than being excused.
- **The hand-run script is gone.** `scripts/plan-catalog-usd-2026-08-11.sql` had already been applied to a database by hand, which is why the values survived a schema reset only as a file. It is now migration `0058` plus `PLAN_CATALOG`, and the two are checked against each other by a seed run that must converge: **`pnpm db:seed` twice produces an identical digest of every priced column and every entitlements blob.** Two sources of truth for a price list is how a screen quotes one number and an invoice charges another.

## Railway, and the hosting option that was never going to work (11 Aug 2026)

- **Two architecture docs listed an option that cannot run this product.** `docs/01` and `docs/03` both offered "Vercel (web) \+ managed Postgres/Redis, **or** Fly.io/Railway for all-in-one" as equal choices. They are not equal, and the first is not a choice at all: `scripts/worker.mts` is a long-lived BullMQ consumer that holds a Redis connection and blocks waiting for jobs, and **Vercel has no process for it to be**. Functions are request-scoped and capped. The line had survived since the master plan because nothing had ever tried to deploy, and a wrong option in a planning doc reads exactly like a right one until somebody acts on it.
- **What it would have cost to find out later.** Taking the Vercel path means replacing BullMQ with a managed runner (Inngest, Trigger.dev, QStash) or cron-triggered functions — a rewrite of the queue module, every sweep's scheduling, and the retry and rate-limit semantics the connectors depend on. That is a rewrite discovered at deploy time, on the day the deadline is real, which is the worst moment to learn that the job system and the host disagree.
- **The decision: Railway, web and worker as two services from one image.** One artifact deployed twice with different start commands. The single image is the load-bearing part — it is what guarantees the worker and the web app run identical code against identical schema. Two images drift, and the drift surfaces as jobs failing against a table the worker has not learned about yet, which looks like a data bug and is a deploy bug.
- **The self-hosted Postgres is a second reason, and it was not the original one.** This database needs `pgvector`, which is why `docker-compose.yml` pins `pgvector/pgvector:pg17` rather than an official image — migration 0008's `CREATE EXTENSION vector` is the first thing that runs and fails without it. Not every managed Postgres offers the extension, so the all-in-one host was already the better fit before the worker settled it.
- **A worker's absence is silent, which is what makes it an operational rule rather than a note.** The web app enqueues into Redis whether or not anything consumes; a queue accepts everything. Deploy only the web service and the digest simply never goes out on Monday, no error anywhere. So **queue depth is the alert**, not process liveness — "oldest job age > N minutes" catches the case where the process is up and wedged, which liveness does not.

## Sentry, and a wizard's scaffold that never ran (11 Aug 2026)

- **The wizard wrote both server configs and wired neither.** `sentry.server.config.ts` and `sentry.edge.config.ts` were generated, committed and inert: nothing imported them. `@sentry/wizard` patches `register()` in `instrumentation.ts`, saw one already there, and backed off — leaving client-side capture only, with two config files on disk that made it look complete. **The failure had no symptom.** This is the same shape as the `next/headers` incident: the thing that is broken is the thing nobody is watching.
- **The obvious place to add the edge import is the wrong one.** `register()` opens with `if (process.env.NEXT_RUNTIME !== "nodejs") return;`, guarding node-only modules. Appending Sentry's import below that guard — where a generated patch lands, and where it reads naturally — means the edge runtime returns before reaching it and edge errors are never reported. The edge init goes **above** the guard, and the comment there says why, because the correct code and the broken code look equally reasonable.
- **The worker needed `@sentry/node`, not `@sentry/nextjs`.** Node resolves `@sentry/nextjs` to its CJS server build, whose ESM named exports come out incomplete — `flush` and `captureException` are both absent, so the shutdown flush could not have been written at all. The two packages are pinned to the same version and one depends on the other, so there is no second copy to drift. Its init is a separate module imported **first** by `worker.mts`, because ES modules evaluate in import order and instrumenting `pg`, `ioredis` and `bullmq` requires being installed before they load.
- **The DSN moved out of the source and into the environment.** The wizard hardcodes it into three files, which points local dev, CI and production at one issue stream — six branches' half-finished errors sitting beside the one that came from a customer. Empty DSN is a no-op, so absent is the safe default and CI reports nothing at all.
- **Two compliance decisions, not preferences.** Bodies, cookies, query strings and auth headers are dropped, `user` is reduced to an opaque id, and **`/r/`, `/u/` and `/c/` token paths are redacted** — those tokens are credentials (`contactBehindToken`), and Sentry access is not the same population as production database access, so an un-redacted one is a working login sitting in a third-party UI. Session Replay records **only on error**, against the wizard's 10%-of-all-sessions: these screens show customers' names, phone numbers and review text, and a standing recording of that is not something to inherit from a default.
- **`deleteSourcemapsAfterUpload` is a security setting, not a cleanup one.** Without it the build emits `.map` files into `.next/static` and the server hands them to anyone who asks — publishing readable source, including the shape of every server action and entitlement check. Sentry keeps its own copy, so only the public one goes away.
- **The wizard's two example routes were deleted, and the test that would have caught them is why they were noticed.** `/sentry-example-page` and `/api/sentry-example-api` are public routes that deliberately throw. `tests/db/public-leakage.test.ts` enumerates public routes from disk and fails when the list grows — exactly what it exists for. The `/monitoring` tunnel route it **cannot** see, because the plugin generates it as a rewrite rather than a file, so it is written down in `next.config.ts` instead.
- **`pnpm worker` was already broken on `main`, and Sentry only surfaced it.** Verifying the worker instrumentation meant starting the worker, which failed at `ERR_MODULE_NOT_FOUND` — confirmed against the committed version, before any of this work. `src/collect/input.ts` imported `@/lib/validation-keys`; Next and Vitest resolve the `@/` alias, plain Node does not. The sibling of CLAUDE.md's worker rule: **a path alias is as node-hostile as a request API**, and both fail only in the process nobody is watching. Worth a completeness test in the style of the others — no worker-reachable module may use `@/` — which does not exist yet.

## The sign-up flow: Google, consent, and a wall moved off the doorway (11 Aug 2026)

Four items in one pass — social sign-in, consent at the point of collection, honest trial copy, and verification-gated sends. Additions to the existing shape, not a rebuild: `emailAndPassword` still works exactly as it did, and every screen it touches keeps its layout.

- **Two Google clients, and the `_AUTH_` infix is load-bearing.** `GOOGLE_CLIENT_ID` already existed and is the **Business Profile connector** — `business.manage` scopes, a consent screen that must clear Google's app review before it may leave testing. Sign-in needs `openid email profile` and no review at all. One client doing both would tie the front door to a review queue: a connector scope added at go-live would put the whole app back into verification, and **until it cleared, nobody could sign in**. Two clients, two variables, named so they cannot be pasted into each other's slot in the one hour when somebody is holding four Google credentials at once.
- **The provider is registered conditionally, and that is the failure mode being avoided.** BetterAuth throws `CLIENT_ID_AND_SECRET_REQUIRED` from inside the authorization-URL builder — *after* the button is pressed. An empty `socialProviders` has no endpoint to press, and `isGoogleAuthConfigured` is the single reader of both variables so the screen and the config cannot disagree. Absent is the ordinary state; it is never a runtime error.
- **`requireLocalEmailVerified` was left at its default of `true`, and the looser setting was tempting.** Account linking asks the *local* row to have proved its address too, so a password account that never clicked the verification email is not linked into and Google sign-in on that address is refused rather than merged. Turning it off would hand the real owner's Google identity to whoever registered their address first. **The way out is the verification email this work adds, not a weaker gate** — and BetterAuth has the option deprecated with the behaviour becoming unconditional, so setting it would buy one release.
- **The mark is `ProviderMark`, not a second Google G.** It already exists for the Connections screen, is already the one place Google's four brand hexes may appear, and drawing another here would give the product two Google marks that drift. Flagged for brand review at go-live: Google's Sign-In guidelines specify their own asset, and a reconstruction is a judgement call rather than compliance.
- **Consent is on *both* auth screens, which is not the obvious reading.** "Continue with Google" on `/sign-in` **creates accounts** — an OAuth arrival with no matching user is a signup wearing a sign-in button. A notice only on `/sign-up` would miss most of the people this product expects. The lead differs by screen (`create` / `continue`) because "By creating an account you accept…" is a small lie to a returning customer, and a consent notice that misdescribes what the reader is about to do is the one copy error that matters here.
- **The terms are stated; only the marketing permission is a checkbox.** Accepting terms in order to have an account is a *condition of the service*, and a tick-box you cannot proceed without is not consent, it is a click. The genuinely optional thing is unticked, separate, and declinable with no consequence. Bundling them is what makes a mailing list unlawful — nobody can tell which half was agreed to.
- **The consent flag comes from the request; the timestamp never does.** `marketingEmailConsent` is a BetterAuth additional field with `input: true` — it is a statement the person is making about themselves, so the request is exactly where it should come from, and the worst a forged `true` achieves is opting its own sender into email. `marketingEmailConsentAt` is declared `input: false` and stamped by a create hook from the clock: **a date the subject could choose is not evidence**. `users_marketing_consent_dated` refuses the contradictory row outright. Nothing sends against either column yet — the record exists before the first send does, the same ordering as the İYS gate.
- **The backfill is "not consented", and that is the honest one.** Nobody who signed up before this migration was ever shown a checkbox, so nobody can be recorded as having ticked one. A default of `true` would have manufactured consent for the entire user table in a single statement.
- **The legal pages are placeholders that say so, prominently, above the text.** Generated legalese is the most dangerous kind of placeholder: it *reads* finished, so it never gets replaced, and the first person to discover it was invented is in a dispute. An Aydınlatma Metni has mandatory contents, and a generated one that omits a required element fails the obligation while appearing to satisfy it. **`/legal/kvkk`, not `/legal/privacy`** — the Turkish document is the one with a legally defined name, and the English copy calls it a privacy notice because that is what an English reader looks for. Both `noindex`: a draft ranking for "Fairfame terms" would outlive its own replacement in the cache.
- **The trial line replaced the subtitle rather than joining it.** Adding "14 days, every feature, no card required" under the button left two nearly-identical grey sentences on one card, and a reader scanning them assumes the repetition is hiding a difference. Every clause is checkable — `TRIAL_DAYS` is 14, the trial grants top tier, no payment method is collected anywhere in the flow.
- **`requireEmailVerification` stays `false`, and the wall moved to the send seam.** The stated target is ten minutes from signup to something worth having, and a verification wall spends the first of those on a round trip to a mail client that may be on another device. What actually needs gating is narrower: **making the product write to somebody else**. Connecting a source, reading the sample workspace, running analysis, replying in-product — all open. `sendOnSignUp: true` is explicit rather than inherited, because with `requireEmailVerification` false the default is to send *nothing*, and the address could then never be proved and every send would be permanently refused.
- **`src/auth/verification.ts` is one module because the alternative is four `if`s that hold until somebody adds a fifth send path.** Same shape as the consent gate: one function decides, every send asks it, a refusal is a named reason. It is deliberately **not** folded into `checkSendAllowed` — that gate answers a question about the *recipient* and is keyed on a `contactId`; this one asks about the *sender*, has no contact in hand, and must cover team invitations, which reach somebody who is not a contact and never pass the consent gate. Conflating them would produce a broadcast refused for "no İYS record" when the truth was an unverified founder.
- **The line is *who chose the address*, not who receives it.** A team invitation is the sharpest case and the least obvious member of the gated three: it goes to somebody the product would call a colleague, but the recipient is free text typed by the sender, and the message carries the business's name to a stranger.
- **Relative imports in `verification.ts`, because the worker reaches it.** `src/auth/session.ts` is one file away, is the obvious place to have put this, and imports `next/headers` — which is why the worker cannot see it. Vitest resolves either perfectly well; only `pnpm worker` fails, at startup, in the process nobody is watching. The same trap as the `next/headers` and `@/` alias incidents above.
- **Asked twice, and the second time is the one that needed thinking about.** `sendBroadcastAction` refuses the person at the button. The **scheduled** send has no actor at all — a broadcast queued on Monday by an unverified account and fired by the sweep on Friday — so the pipeline reads the *creator's* verification at send time, beside where it re-reads the plan. **A null creator is skipped, not refused**: that is a system broadcast, and refusing it would block the one sender that cannot possibly be a throwaway signup.
- **The refusal is translated centrally, in `useAction`, beside the `INVALID_INPUT` case.** It surfaced in English on a Turkish screen, because the server writes its sentence at the throw where nobody knows who is reading. Translating per call site would mean the same sentence written four times and drifting immediately — reintroducing on the client the exact problem `verification.ts` solves on the server.
- **A toast is necessary and not sufficient, so there is a banner too.** A refusal that arrives *after* a campaign has been written and the button pressed teaches the rule at the most expensive possible moment. The banner names the three things that wait, which by omission tells everybody else they can ignore it — and that honesty is what keeps it credible for the people it does concern. Not dismissible: a banner you can permanently hide is one somebody hides in week one and rediscovers in week six, mid-campaign, via a toast.
- **Two existing suites went red, and both were right to.** `tests/db/broadcasts.test.ts` builds admins with `emailVerified` at its default of `false`, so every broadcast in the file was abandoned before the consent assertions ran — they would have passed having proved nothing. The fixtures now say `emailVerified: true`, because an ordinary sending admin is verified, and the unverified case has a suite of its own. **A fixture that quietly carries two conditions tests neither.**
- **The e2e setup verifies through the real link out of Mailpit, not by flipping the column.** An account verified by an `UPDATE` proves the product nothing — the token would never be minted, the callback never hit, and a broken verification link would sail through a green suite. Same argument `createAccount` already makes for building accounts through the product's own endpoints.

## Organization creation, gated on the plan (11 Aug 2026)

Asked whether `/create-organization` was restricted by plan. It was not — in a way worth recording, because the check was not *bypassed*, it was **structurally absent**.

- **There was no seam to put a check in.** `CreateOrganizationForm` called BetterAuth's `organization.create` straight from the browser. No server action stood between, so the entitlement layer was nowhere on the path. The only cap was `organizationLimit: 20` in `src/auth/config.ts`, whose own comment calls it a backstop against runaway creation rather than a plan rule — and the plan model could not express one anyway, because `LIMIT_KEYS` had no key for it.
- **The cost was free trials, not workspaces.** Every organization gets its own 14-day trial from `afterCreateOrganization`. Twenty workspaces was twenty full-feature trials on one account — 280 trial-days, no card — against a business model that prices the trial explicitly to *bound* AI and SMS spend (`docs/05` §2.1).
- **`max_organizations` is the odd key in the catalog and says so.** Every other limit is a property of an *organization*, counted inside its tenant. This is a property of a **user**, asked by somebody who may have no organization at all. It lives in the catalog because the numbers are a pricing decision — Starter 1, Growth 2, Pro 3, Agency unlimited — and hardcoding them would be the `if plan === '...'` the architecture forbids.
- **`withinLimit` throws if handed it, rather than answering.** There is no resource counter for the key, so `readUsage` would fall through to `usage_counters`, find nothing and return `0` — a check that passes forever while reading exactly like an enforced one. That is this codebase's recurring failure: not a missing guard but a **confident wrong** one. `src/auth/organization-limit.ts` owns the question.
- **Ownership, not membership.** Only organizations where the person is `owner` count. An accountant invited into a client's workspace must not lose the ability to create their own, and an agency inviting ten people must not consume ten allowances.

Not a loophole — the allowance disappears with the subscription that granted it.

Applying that here would make `max_organizations` unlimited for every new account — and since each new organization mints another trial, "unlimited workspaces while trialing" *is* "unlimited trials". The rule would grant the thing it exists to bound. A prospect evaluating for two businesses subscribes first, which is the correct order: the second workspace is the thing being sold.
- **Adding a key to `LIMIT_KEYS` is a breaking change, because the safety net is real.** `loadSubscription` validates `plans.entitlements` against the widened schema on *every* resolve, so without migration 0061 the first entitlement check after deploy throws for every organization on a seeded plan — which is all of them. Swapped for `aria-required` plus `FieldError`; `tests/lib/action-feedback.test.ts` caught it.

## Stripe: lookup keys, a money bug, and the two line items nobody was charging (11 Aug 2026)

Setting up the Stripe catalog surfaced four problems, one of them expensive.

- **Inline `price_data` mints a Product per checkout session.** `stripe.ts` built its line item from `PLAN_CATALOG` with an inline `product_data: { name }`, on the documented argument that one source of truth beats a dashboard that can drift. The argument was right about drift and wrong about the cost: Stripe creates a **new Product and Price for every session** built that way. The orphaned "Revira Pro" in the sandbox was not made by hand — one checkout made it. At any volume the dashboard fills with duplicates and Stripe's revenue reporting, which groups by product, stops meaning anything.
- **The fix keeps the catalog authoritative and moves the drift check into a command.** Prices are pre-created and found by `lookup_key`; `pnpm stripe:sync` reconciles them with `PLAN_CATALOG` and **exits non-zero** when they disagree. Read-only by default like `pnpm golive` — a script that writes the moment it is run is one nobody dares run to *look*, and looking is the common case. It refuses `--apply` against a live key outright: live prices get made in the dashboard by a person.
- **Drift is reported and never repaired.** A Stripe Price is immutable, so "fixing" one means creating a new price and moving the lookup key across — which re-prices nothing for existing subscribers until somebody migrates them deliberately. That is a decision with money attached and the script declines to make it. Missing prices *are* creatable, because creating one changes nothing for anybody who has already paid.
- **The money bug.** The inline version charged `unit_amount: plan.priceMonth` in `request.currency`, and `PLAN_CATALOG` is **USD cents by decision**. So an organization whose currency was TRY was charged `22900` *lira units* — **₺229 instead of roughly ₺8,000** — silently, on a correct-looking invoice. Looking the price up removes the possibility: a Price carries its own currency and there is nothing left for a caller to reinterpret.
- **Annual and per-location extras existed in the catalog and in no invoice.** Checkout sent one line item at `priceMonth`, quantity 1, so `priceYear` and `priceExtraLocationMonth` were priced, documented, and unreachable. Both are now line items.
- **The add-on quantity is computed server-side and is not in the request.** `extraLocationsFor` counts the organization's live locations against `includedLocations`. A caller that could name its own quantity could name `0`, and a fifty-branch chain would check out at the one-branch price. Same reasoning as `intentFor` in the messaging gate: the number that decides what is charged is derived, never passed.
- **`expectedPrices()` is derived from the catalog rather than listed.** Pricing an add-on that was previously `null` puts a new row in the sync worklist with nobody remembering to add one — and `null` stays absent rather than becoming a real Stripe price charging zero, which is `docs/15`'s "absence is null, never 0" with money attached.
- Verified against the sandbox: 12 prices reconcile; a deliberately edited catalog amount was caught as `DRIFT` with a non-zero exit, then restored.

The service was added, **plus `EMAIL_TRANSPORT=smtp`** — the default `log` transport renders mail without sending it, so the container alone would not have been enough — and the helper now probes reachability once, separately, so "no inbox is listening" and "the mail never arrived" produce different sentences. The docblock's wrong claim is left in the file with the correction beside it.
- **The second was the opposite mistake.** `PlanSection` renders the billing-period toggle only under `canManage && canCheckout`, so with no provider configured — the repo's default — `e2e/plan-toggle.spec.ts` asserted a control that was never drawn. Fixed on both sides: CI gets a fake `STRIPE_SECRET_KEY` so the browser suite exercises the paid path (otherwise CI is the one place the branch customers actually see is never tested), and the spec asks the app which state it is in rather than assuming, the way the Google-button spec already had to learn to.

**And that key exposed something worse.** Three tests in `tests/lib/billing.test.ts` went red. Two were right to: `providerForCurrency` prefers a *configured* provider over a merely preferred one, so TRY correctly moved from iyzico to Stripe — the tests asserting "TRY routes to iyzico" were describing an unconfigured machine rather than the rule `src/billing/registry.ts` documents. The third made a real HTTP request to Stripe from `pnpm test` and got a 401.

- **The 401 is the lucky version.** That test asserts `createCheckoutSession` *refuses* when nothing is configured. With a **valid** key it would not have failed at all — it would have created a live Stripe object from a unit test, and the suite would have stayed green while doing it.
- **So the environment is the fix, not the variable.** `tests/setup-unit-env.ts` had claimed since Phase 0 that "nothing in this suite connects to anything", and enforced it with `??=`, which only ever *adds*: an inherited credential passed straight through untouched. The claim held because no developer happened to export one. It now **deletes** them — payment, model, messaging, platform, Sentry — before the first test loads. A test that needs one sets it itself and restores it, which `billing-checkout.test.ts` and `provider-flags.test.ts` already did and are more honest for.
- **`tests/lib/test-env-seal.test.ts` is the completeness half.** The rule this file states elsewhere — a completeness test is not a behaviour test, and both are needed — applies to environments too: the next version of this is one named assertion about a sealed variable rather than three puzzling failures in a billing file nobody touched.

The rule that comes out of it: **a test asserting a refusal is asserting something about its environment, and an environment that is not pinned is not a precondition.** Both directions cost a day — one where CI lacked what the suite assumed, one where it held what the suite assumed absent.

## Four variables the app had never heard of (12 Aug 2026)

"Is our `.env` in step with `.env.example`?" is a five-minute question, and the answer was yes — every key set locally was documented, and the thirteen the example carried and `.env` did not were all blank optional placeholders. Comparing both against `src/lib/env.ts` is what found something.

**`pnpm mock:platform` printed four variables to copy into `.env`, and not one of them existed.** `GOOGLE_ACCOUNT_MANAGEMENT_BASE_URL`, `GOOGLE_BUSINESS_INFORMATION_BASE_URL`, `GOOGLE_REVIEWS_BASE_URL` and `META_GRAPH_BASE_URL` were in no schema and read by nothing in `src/`. The Google and Instagram clients each took a base URL as a constructor option, and nothing outside a contract test had ever passed one. So the fake Google and fake Meta sat there answering requests that were never sent to them, and a developer following `CLAUDE.md`'s "point the connectors' base URLs at it" pointed a connector holding no credentials at the real `mybusinessaccountmanagement.googleapis.com`. The failure looks exactly like a broken connector.

- **The quiet ones cost the most.** Nothing breaks when a variable is documented and unread: the app boots, the schema is satisfied, the paste succeeds. It is only discovered by somebody setting the thing up and finding it had no effect, which is the most expensive moment to discover anything.
- **`WHATSAPP_BASE_URL` became `META_GRAPH_BASE_URL`.** The schema *did* carry a base URL for the messaging client under a third name, which is how this survived: WhatsApp worked, so the variable looked wired. One Meta app, one Graph API, one variable — Instagram and WhatsApp read the same one now, and the name matches what the script has always printed rather than the script being changed to match the code.
- **Option, then environment, then the real host.** A contract test passing an explicit base URL must still win over whatever a developer left in `.env`, and the absent case must be Google's and Meta's own hosts, because that is the only correct answer for a customer. All three are asserted.
- **Read inside the factory, not at module load**, so a test that sets a variable and resets the cache is answered, and so importing a connector never depends on a validated environment.

Both halves are pinned, because they fail differently. `tests/lib/env-example.test.ts` is the completeness half: every key in the schema is documented, nothing is documented that the app does not read (bar `APP_DB_USER`/`APP_DB_PASSWORD`, which Docker consumes and Zod never sees), and **no script tells anyone to set a variable that does not exist** — derived from `ENV_KEYS`, which is `Object.keys(envSchema.shape)` rather than a list somebody maintains. `tests/lib/connector-base-urls.test.ts` is the behaviour half, asserting the URL the client actually fetches, since the entire bug was a value that existed and was carried nowhere.

Verified the way the claim deserved: with `pnpm mock:platform` running, the real `createGoogleClient` and `createInstagramClient` — configured through `.env` and nothing else — returned `accounts/106321548215487` and `@kahvemolasi` from the fake. That promise has been in `CLAUDE.md` since Phase 1b and this is the first time it has been true.
